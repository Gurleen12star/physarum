The problem

Your graph still thinks it's 2020.

Graphs are built once by extractors and then frozen. When the world changes, the new fact is appended but the old one is never removed, and the hallucinated facts stay too. Retrieval can't tell which is current, so agents confidently answer with yesterday's truth.

Vector search makes it worse: a false or outdated fact is exactly as similar to the question as the true one. Similarity isn't truth, and it isn't time.

Physarum closes the loop. The signal is the cheapest one you already have: was the answer right?

Complementary, not either/or: Mem0 and Graphiti decide what to write. Physarum learns which written facts to trust from how answers land, and can sit on top of any graph they build.

How it works

Three steps on every answer.

01 · Traverse

One native HydraDB call

algo.SSpaths ranks candidate paths by learned resistance r = L/D, stored on each edge as weightProp.

02 · Verdict

One bit of feedback

A user's 👍/👎, or an LLM judge checking each fact. That's the only supervision; it's noisy, and that's fine.

👍👎🤖 judge
03 · Physics

Tubes grow or starve

Food at the right answer → Kirchhoff flow → tubes that carried it thicken. Wrong answers light up their path and it retracts. Written back in one batched query.

Why Physarum

A graph that gets sharper every time it's used.

01

Learns from one bit

No labels, no training pipeline. A thumbs-up or thumbs-down on the final answer is enough; Kirchhoff's laws decide which edges earned the credit.

02

Heals when the world changes

Plastic tubes re-weigh old evidence on every use, so a superseded fact is unlearned in a few votes, not hundreds. Shown live on real 2020→2026 changes.

03

Audits its own facts

Tubes that keep starving are facts the graph stopped trusting. Physarum hands you the list, checked against human-verified labels.

04

Knows when it's unsure

When flow splits almost evenly between answers, it flags the answer as uncertain, so users and agents know which answers to double-check.

05

Explains every answer

Click any answer to see the path, the flow through each tube, and every verdict that shaped it.

06

Forgetting is free

Evaporation is a single global scale factor: zero database writes, instead of touching every edge on every step.

Built on HydraDB

Two queries. Their engine. It learns.

Learned state lives on HydraDB edges, in object storage, so every agent and every app instance reading the graph benefits from every verdict, and it survives restarts.

// 1 · retrieve: ranked inside HydraDB by what the graph has learned
CALL algo.SSpaths({
  sourceNode: $person, relTypes: ['P27','P35'],
  maxLen: 2, weightProp: 'r'       // r = L / D
}) YIELD path RETURN path

// 2 · learn: one batched write per verdict
UNWIND $rows AS row
MATCH (s:Entity {id: row.s}), (d:Entity {id: row.d})
MERGE (s)-[r:P35 {id: row.e}]->(d)
SET r.R = row.R, r.acc = row.acc,
    r.rej = row.rej, r.r = row.r

FAQ

Questions judges ask.

Where does the feedback come from in production?

Any answer-level signal: a user's 👍/👎, an LLM judge checking the cited facts, or a downstream success signal (the ticket got resolved, the PR merged). In the demo, you are the verifier, or you can hand it to the built-in judge.

Why not just use vector RAG?

We measured it: hybrid RAG (dense vectors + TF-IDF keywords, reciprocal rank fusion) with a generous two-hop reader. When it retrieves the right person's facts, it still can't tell a true fact from a plausible false one, and after the 2026 changes it keeps retrieving the outdated head of state. It also never improves with use, and it spends about 10× more context tokens per answer than following one learned path.

Isn't this just counting votes per edge?

No, and we measured it. A count-only learner is in the comparison table. It learns, but when facts change it gets stuck behind its own history. Physarum's plastic tubes and Kirchhoff credit assignment are what let it unlearn.

Are the 2020 → 2026 changes real?

Yes. Heads of state that actually changed (Elizabeth II → Charles III in 16 realms, Havel → Petr Pavel, John Paul II → Leo XIV), with sources. scripts/fetch_wikidata_changes.py regenerates them from live Wikidata.

What does it cost to run?

One read query and one batched write per answer, plus four numeric properties per edge. Forgetting costs zero writes.

Where does it lose?

On a graph where nothing changes, simple vote counting learns about as well as Physarum; its edge is when facts change, plus a sharper self-audit. Rarely asked facts learn slowly, because no traffic means no evidence. The audit flags about 80% true positives, not 100%. The README has a full "where we lose" section.
